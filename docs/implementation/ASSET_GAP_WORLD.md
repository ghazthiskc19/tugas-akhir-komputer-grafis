# Penutupan Gap World — Sumber Spesifik dan Adaptasi Agent

Tanggal riset: **20 November 2026**. Acuan: [audit ekosistem](ASSET_ECOSYSTEM_AUDIT.md), [register world](ASSET_ECOSYSTEM_WORLD.md), dan [inventaris M01–M28](ASSET_INVENTORY.md). Inti tetap **KayKit Adventurers + Character Animations + Forest + Dungeon**. Dokumen ini mencari bahan untuk M16/M17/M18/M24/M26/M28, bukan menambah katalog world generik.

**Hasil:** ada jalur tambahan **USD 0** untuk motif glyph, connector lurus/siku, crystal, seal dan shader/VFX. Resource Bits Extra **tidak wajib untuk crystal**. Namun tidak ditemukan satu paket yang sudah menyediakan puzzle/gate/gameplay persis. Relief, altar, tiga sockets dan adaptasi renderer masih pekerjaan agent dari sumber online yang disebut di bawah, **belum fulfilled/VERIFIED**. Tidak ada download model/ZIP, install, import, pembelian, login, atau tes Godot; yang dibaca hanya halaman, manifest publik, source teks dan **dua preview**. Status produksi inventaris tidak berubah.

## 2. M16 — empat glyph dan relief urutan

**Pilihan konkret dari preview G01:** hitung baris/kolom mulai 1 pada grid rune utama, bukan enam contoh style di bawah.

| ID usulan project, bukan filename pembuat | Lokasi preview G01 | Bentuk yang terlihat |
|---|---|---|
| `glyph_cross` | baris 2, kolom 1 | Dua diagonal menyilang/X |
| `glyph_arrow` | baris 1, kolom 8 | Panah ke atas dengan batang |
| `glyph_fork` | baris 2, kolom 8 | Percabangan tiga ujung di atas batang |
| `glyph_diamond` | baris 3, kolom 11 | Belah ketupat tertutup |

Keempatnya benar-benar berbeda motif, bukan empat recolor. Ini pemilihan visual dari gambar pembuat, **bukan klaim nama file atau arti rune historis**. Seluruhnya tetap simbol fiksi di game.

**Rencana edit agent:** pisahkan empat motif dari vector G01; buang frame stone 2D; jadikan kurva tertutup dengan ketebalan konsisten, extrude tipis sebagai relief anak pada G02 `pillar.fbx`. Untuk relief petunjuk, letakkan empat motif yang sama pada satu backing G02 `floor_tile_small.fbx` yang dilebarkan. Jadikan warna batu/material seperti Dungeon, bukan menempelkan background biru preview. PNG/spritesheet adalah sumber alternatif jika vector tidak dapat dipakai; tracing motif sumber dan ekstrusi tetap pekerjaan baru agent, bukan mesh yang disediakan pack.

**Risiko MEDIUM:** stroke arrow/fork harus tetap berbeda dari kamera; lubang diamond harus bertahan saat bevel/decimation. Jangan memakai `Decal` node sebagai persyaratan karena Compatibility tidak mendukungnya (§5). Pilihan aman adalah mesh relief atau plane bermaterial alpha dengan offset kecil.

**Belum fulfilled:** file vector asli, ketebalan relief, UV/material, jarak baca, dan urutan yang dipasang sesuai state puzzle belum diuji. Urutan clue dan pemeriksaan input berada di GDScript; paket rune tidak menyediakan perilakunya.

## 3. M17 — panel energi lurus dan siku

**Basis spesifik G03:** `track-straight.glb` → jalur lurus; `track-corner.glb` → jalur belok. Nama path didukung manifest resmi, bukan inferensi dari label “120 models”. Tidak perlu mengimpor mobil, audio atau logic racing. README menyebut template Godot 4.6; [project sumber](https://raw.githubusercontent.com/KenneyNL/Starter-Kit-Racing/main/project.godot) memakai **Forward Plus**, sehingga template itu sendiri **bukan bukti renderer Compatibility**. Model GLB dapat dinilai terpisah dari renderer demo.

**Rencana edit agent, bukan asset siap:** isolasi strip permukaan track, hapus dinding/marking balap yang tidak sesuai, pipihkan dan seragamkan ketebalan; scale supaya pusat dua ujung tepat pada pusat sisi panel G02. Set belokan menjadi sambungan dua sisi bersebelahan; cek sudut aktual pada mesh sebelum menyebutnya 90°. Bake transform, rapikan UV mengikuti aliran, beri stone rim dan strip cyan memakai material V01 yang diadaptasi. Backing tetap KayKit Dungeon. Bila corner awal melengkung, itu boleh menjadi elbow melengkung selama endpoint grid tepat; tidak mengubah aturan koneksi.

**Risiko MEDIUM–HIGH:** pemisahan surface/UV belum diketahui; kerb/bank yang menyatu dapat memerlukan mesh edit lebih dari scale. Sumber online geometri lurus/belok kini konkret, tetapi biaya edit belum dibuktikan rendah. Tidak mengganti puzzle dengan track balap.

**Runtime masih implementasi:** tiga panel, pivot tengah, rotasi kelipatan 90°, port bitmask/adjacency, evaluasi source→target dan animasi aliran hanya pada jalur tersambung. `TIME` dalam shader hanya menggerakkan texture; itu tidak memeriksa koneksi. Belum fulfilled sampai ujung modul, seluruh orientasi, pivot, UV dan feedback benar/salah diuji.

## 4. M18 dan M24 — crystal, altar, seal, gate tiga sockets

### Crystal dan altar tanpa Resource Extra

Pilih **G04 Crystal iPoly3D**, bukan membeli Source/Extra untuk satu bentuk. Preview kedua menunjukkan shard tinggi ramping berwarna biru; **[INFERENCE]** pemendekan sumbu tinggi dan pembesaran lebar dapat mendekatkannya ke proporsi chunky KayKit, tetapi normal/material perlu dirapikan setelah bake scale.

Altar: G02 `column.fbx` dipendekkan sebagai pedestal di atas `floor_tile_small_decorated.fbx`; crystal menjadi child terpisah, bukan di-merge supaya hover/pulse dapat dianimasikan. Seal besar: ulang empat motif vector G01 mengelilingi backing batu dan gunakan V01 untuk ring feedback. G05 tersedia bila seal PNG kecil cukup; 83×83 bukan opsi close-up yang setara vector. **Risiko MEDIUM**, termasuk komposisi, material cyan/stone, seating crystal dan readability. Belum ada bukti pedestal dengan nama “altar” atau “seal” siap pakai.

### Tiga sockets harus matching artefak, bukan tiga lampu

**Basis gate:** G02 `wall_arched.fbx` + `pillar.fbx`; `wall_gated.fbx` hanya alternatif setelah diperiksa apakah bagian pintunya terpisah. Agent menambah tiga mounting plate dari tiga instance `floor_tile_small.fbx`, bukan mencari gate generik lalu mengklaim sockets sudah ada.

**Rencana pasangan artefak/socket berbasis motif online:** gunakan bentuk G01 **cross, fork dan diamond** sebagai tiga key-head/relief artefak; pasang pada fragmen backing batu G02 dengan crystal G04 sebagai aksen. Extrude motif yang sama menjadi cutter untuk recess pada masing-masing plate gate. Dengan demikian bentuk lubang dan key-head berasal dari path sumber yang sama, bukan tiga recolor. Lubang diamond harus mempertahankan island bagian tengah; sambungan cross/fork perlu ketebalan yang tidak rapuh. Agent menangani seluruh mesh edit/Boolean, cleanup dan pemasangan; tidak memerlukan pengguna menggambar/model manual.

Ini **rencana authoring turunan yang terarah**, bukan klaim tiga artefak atau socket mesh tersebut sudah ada di ZIP KayKit. **Risiko MEDIUM–HIGH**: Boolean/non-manifold/bevel dan bagian tengah diamond bisa memerlukan perbaikan topology. Stable IDs, deteksi inventory, pengisian socket, animasi pembukaan gate, reset dan collision arena tetap GDScript/AnimationPlayer. Bila gate ternyata satu mesh utuh, split mesh/pivot harus diselesaikan, bukan menyebutnya siap animasi.

**Bukti yang masih diperlukan:** tiga silhouette terbaca tanpa mengandalkan warna; setiap key-head benar-benar cocok dengan recess; gate opening tidak menembus artefak; collision tidak menghalangi pemain ketika terbuka. M19 ikut terpengaruh karena artefak harus menggunakan pasangan bentuk yang sama; dokumen ini tidak mengubah inventaris atau menetapkan statusnya.

## 5. M26 — water shader dan batas Compatibility yang diverifikasi

Sumber resmi engine yang dibaca adalah **Godot stable 4.7**: [Overview of renderers](https://docs.godotengine.org/en/stable/tutorials/rendering/renderers.html), [Spatial shaders](https://docs.godotengine.org/en/stable/tutorials/shaders/shader_reference/spatial_shader.html), dan [Advanced post-processing](https://docs.godotengine.org/en/stable/tutorials/shaders/advanced_postprocessing.html). Ini bukti API/fitur, **bukan uji project 4.7.2** dan bukan water shader turnkey resmi Godot.

Fakta penting dari dokumentasi resmi:

- Compatibility menggunakan OpenGL; mendukung **screen texture dan depth texture**, tetapi **tidak** normal/roughness buffer, SSR, compute shaders, Decals atau particle trails. Jangan menyatakan setiap depth shader otomatis Forward+-only, atau sebaliknya setiap shader Godot 4 pasti Compatibility-safe.
- NDC depth Compatibility adalah **−1…1**, bukan 0…1. Formula yang diberikan resmi: `vec3 ndc = vec3(SCREEN_UV, depth) * 2.0 - 1.0;`. Gunakan branch `CURRENT_RENDERER == RENDERER_COMPATIBILITY` bila satu shader melayani beberapa renderer. Rekonstruksi world position resmi adalah `(INV_VIEW_MATRIX * INV_PROJECTION_MATRIX * vec4(ndc, 1.0)).xyz / w`.
- `TIME`, UV, VERTEX, ALBEDO, ALPHA, `blend_add`, `unshaded`, `cull_disabled`, dan `world_vertex_coords` didokumentasikan. Menulis ALPHA memindahkan material ke transparent pipeline, sehingga sorting tetap perlu diuji. `TIME` tidak berhenti hanya karena scene tree pause; combat progress yang harus berhenti/resume perlu uniform/state project.

### Audit kode W01, bukan percaya judul “all pipelines”

1. [**`shaders/64-water-imposter.gdshader`**](https://raw.githubusercontent.com/taillight-games/godot-4-pixelated-water-shader/main/shaders/64-water-imposter.gdshader) adalah basis paling sederhana: dua sample noise UV yang bergerak, sample color-gradient, ALBEDO, ALPHA 1. Tidak membaca depth/screen, normal buffer atau SSR. **[INFERENCE] kandidat adaptasi Compatibility berisiko lebih kecil**, bukan jaminan visual siap; perlu gradient/noise `.tres` dari repo atau resource engine. Agent dapat menghapus output ALPHA konstan saat menjadikannya ocean opaque agar tidak masuk transparent pipeline tanpa kebutuhan.
2. [**`shaders/n64-water.gdshader`**](https://raw.githubusercontent.com/taillight-games/godot-4-pixelated-water-shader/main/shaders/n64-water.gdshader) menambahkan vertex waves, normal, depth coloration dan screen refraction. Namun source yang dibaca memakai `vec3(SCREEN_UV * 2.0 - 1.0, depth2)` **tanpa branch Compatibility**, dan menambah `CAMERA_POSITION_WORLD.y` setelah inverse view/projection. Ini tidak sama dengan formula world reconstruction resmi. **Jangan menjanjikan versi ini langsung benar di Compatibility**; port depth dan periksa rekonstruksi world sebelum dipakai.
3. [**`shaders/water-foam-pass.gdshader`**](https://raw.githubusercontent.com/taillight-games/godot-4-pixelated-water-shader/main/shaders/water-foam-pass.gdshader) menyediakan source vertex-wave/noise yang dapat dipakai agent sebagai basis animasi; `sync_time` harus diisi atau diganti TIME bila sinkronisasi gameplay tidak dibutuhkan. README menjelaskan foam mask memakai orthographic Camera3D + SubViewport, bukan magic shoreline dari sebuah tile.

**Jalur pilihan:** turunkan W01 menjadi material ocean stylized opaque dengan scroll noise/gradient dan gelombang vertex dari source tersebut; samakan palette Forest/Dungeon. Untuk shoreline gunakan mask/strip foam yang dirakit agent sesuai coast, atau implementasikan sistem mask SubViewport W01 jika memang dibutuhkan. Itu bukan janji pantai otomatis. Jika transparansi/depth fade dipilih, perbaikan formula di atas menjadi prasyarat, bukan alasan menghapus requirement air.

Geometry permukaan/shore memakai base online yang sudah dipilih (misalnya KayKit Medieval `hex_water.gltf`/coast dari audit world), atau mesh permukaan adaptasi agent; **shader bukan model pulau**, dan tile air bukan shader. WorldEnvironment, sky, matahari, fog, ukuran laut, seam/horizon serta collision batas laut tetap setup project. Risiko **MEDIUM** untuk turunan opaque; **HIGH** untuk port full refraction/depth/foam. Belum ada compile/render/profile 4.7.2 atau bukti seluruh M26 selesai.
